Chronos Livechat to Alarms Exploration

Rendered map of the current code shape, integration decisions, and recommended path.

Goal / finding Inspection Decision Recommended work Risk
Goal: analyze livechat integration into alarms Explore the current Chronos app and identify how a LiveKit-powered chat/voice assistant can operate the alarm section.
Repo shape Expo mobile app, FastAPI server, SQLite calendar service, and LiveKit Python agent. README.md
Alarm code Alarm tab renders static local data. AlarmKit is only a JS wrapper with a native bridge placeholder. AurelianCalendarScreen.tsx:38,397; alarmkit.ts:16
LiveKit code Token request path exists and the agent can join a room, but no room/chat UI is mounted in mobile. livekit.ts:14; main.py:124; agent/main.py:15
Calendar persistence Calendar events are derived from timeline_items. There is no alarm table or alarm API. db.py:41; calendar_service.py:99,252
Decision: create an alarm domain Alarms need their own lifecycle, enabled state, native ids, smart rules, and sync status. They should link to events, not be hidden inside event rows.
Decision: split source of truth The server owns alarm intent and smart rules. The mobile app owns native AlarmKit execution because iOS permissions and scheduling are device-local.
Server API Add alarms table and CRUD endpoints, plus optional preview/recompute endpoints for AI suggestions.
Agent tools Add typed LiveKit function tools: list events, create alarm, update alarm, cancel alarm.
Mobile client Replace static alarm rows, add LiveKit room UI, schedule through AlarmKit, and PATCH native scheduling result.
Risks iOS-only behavior, authorization denial, timezone correctness, AI confirmation accuracy, and server/native sync failures.
Finding Feasible with the existing stack, but real livechat alarm scheduling should land after alarm persistence and typed agent tools are added.

Recommended Runtime Flow

1. Open chatUser enters LiveKit chat/voice from Alarms.
2. Join roomMobile calls /livekit/token and connects.
3. InterpretChronosAgent understands alarm intent.
4. Tool callAgent calls create_alarm or update_alarm.
5. PersistServer stores alarm intent and linkage.
6. Native syncMobile calls AlarmKit.scheduleAlarm.
7. ConfirmMobile patches native_alarm_id or failure.
